# 7. Reserve the aerofoil namespaces before the first release

* Status: Proposed
* Date: 2026-11-04
* Deciders: Colin Wolff
* Related: `docs/ROADMAP.md` §0, `Cargo.toml` `repository`, `storypole` `AF-20`, `AF-21`

## Context and Problem Statement

The names have to be held before anyone else takes them, but two platforms behave differently:

* **crates.io has no reservation API.** A name is held only by publishing at least one version, and a
  published version can be *yanked* but never deleted, so the first release of each crate is
  permanent public history.
* **GitHub `aerofoil` is not available.** Checked 2026-11-04: `api.github.com/orgs/aerofoil` returns
  404, but `api.github.com/users/aerofoil` returns a **user** account created 2023-12-27 (display
  name "aerodyne"). A taken username blocks an organisation of the same name, so
  `github.com/aerofoil` cannot be claimed — a second-choice handle would be needed.

Availability checked against the crates.io API on 2026-11-04 — all eight return 404, i.e. free:

`aerofoil`, `aerofoil-common`, `aerofoil-1090`, `aerofoil-978`, `aerofoil-tracker`,
`aerofoil-server`, `aerofoil-cli`, `aerofoil-mcp`.

The `gaugeblock` suite already has a convention for this (`gaugeblock/AGENTS.md` §2): **namespace
reservations publish at `0.1.0-alpha.1`**, and a placeholder is never a `beta` — the crate moves to
`0.1.0-beta.1` on its first real, dogfood-ready build. Sibling crates were reserved by a script that
scaffolds a staging tree and publishes from it.

Forces:

* **Irreversibility.** A wrong first publish cannot be undone, only yanked; a squatted name is gone.
* **Ownership is separable.** crates.io owners can be added and removed (`cargo owner`), and GitHub
  repositories can be transferred with redirects. Holding names under one account today does not
  commit the project's long-term ownership.
* **Consistency.** All nine sibling repositories live under the existing `gaugeblock` organisation,
  and `Cargo.toml` already declares `https://github.com/gaugeblock/aerofoil`.
* **Lockstep SemVer.** The reservation version is a workspace-wide decision: `0.1.0-alpha.1` here
  means every crate published for this project starts there.
* **Placeholders versus the real crates.** Six of the seven crates do not exist yet; publishing them
  from the real workspace would need placeholder packages as workspace members, which `AGENTS.md` §7
  forbids as vacuous (a gate that passes over a package with no behaviour).

## Considered Options

1. **Personal account throughout.** `github.com/colinwolff/aerofoil`, crates owned by the personal
   crates.io account. Fastest, no new handle; but the suite's identity fragments and a future
   transfer touches every published crate's owner list.
2. **Existing `gaugeblock` organisation for repositories; crates published from the maintainer's
   account, with the organisation added as an owner as maintainers arrive.** Keeps the manifest URL
   that is already declared, matches all nine siblings, and needs no new handle.
3. **A new organisation.** `aerofoil` is taken, so this means a fallback handle (`aerofoil-labs`,
   `aerofoil-rs`, `aerofoil-hq`) — a new identity that has to be kept in sync with a suite that
   already has one.
4. **Defer all reservations until the first beta.** Zero placeholder history, but leaves all eight
   names exposed for the whole of M1–M4. Rejected by inspection: `aerofoil` is a common aviation
   term, and the cost of losing it is permanent.

## Decision Outcome

**Undecided.** Stays `Proposed` until confirmed; `storypole ask-decision` on `AF-20` blocks the
publishing task until it resolves.

**Recommended outcome (option 2), for confirmation:**

* Repository: `https://github.com/gaugeblock/aerofoil` — the URL already declared in `Cargo.toml`.
* crates.io: publish from the maintainer's account so the names are held immediately; add the
  long-term owner (organisation or additional maintainers) as an owner while that is cheap, rather
  than transferring later.
* Reservation mechanics: eight placeholder crates at `0.1.0-alpha.1`, scaffolded into a gitignored
  `reserve-staging/` tree by `scripts/reserve-namespaces.sh` and published from there — no
  placeholder packages in the real workspace. Real crates publish `0.1.0-beta.1` when dogfood-ready;
  each placeholder is yanked once its real counterpart exists.

The reason this is low-risk to decide now: the two irreversible facts are the *crate names* and the
*first published version*, not the account. Numbers and owner lists can be corrected; a name somebody
else published cannot.

### Positive Consequences of deciding as recommended

* The eight names are held in one sitting, before M1 work makes the project more visible.
* The version ladder matches the suite (`alpha.1` reservation → `beta.1` dogfood), so `0.1.0` keeps
  its meaning: first release anyone should depend on.
* No placeholder packages in the workspace, so `cargo check --workspace` keeps meaning something.

### Negative Consequences

* A placeholder release is permanent clutter in the index until its real crate supersedes it, and
  crates.io's publish rate limit means the eight publishes span several minutes.
* `aerofoil` cannot be an organisation on GitHub; if a distinct identity is ever wanted it must be a
  second-choice handle, and that decision is cheaper to take now than after the repo has stars.
