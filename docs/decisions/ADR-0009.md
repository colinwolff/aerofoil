# 9. Choose the persistence seam, not the storage engine

* Status: Accepted
* Date: 2026-11-04
* Deciders: Colin Wolff
* Related: `ADR-0005`, `docs/ROADMAP.md` M3/M4/H3, `docs/SPEC.md` §5, `storypole` `AF-24`

## Context and Problem Statement

Nothing in the specification says where decoded data goes, and "we need storage" conflates four
different problems that have different answers:

| Need | Shape | Candidate |
| :--- | :--- | :--- |
| Recording and replay | append-only, written once, read sequentially | JSONL, Parquet |
| Config and registry | tiny, mutable, transactional | SQLite, redb |
| History and analytics | growing, queried by time and space | SQLite → PostgreSQL / ClickHouse |
| Live track state across restarts | — | **not wanted** (see below) |

Three facts decide most of this before any benchmark runs:

* **The state of record is the air, not a disk.** Frames keep arriving at 1–10 Hz per aircraft, so a
  restart loses seconds that the feed refills. Persisting live track state would put an fsync on the
  hot path to buy back state the receiver regenerates anyway, against `PROJECT.md`'s success
  criterion of bounded memory and no unbounded queues.
* **The volume is small.** 200 aircraft at 1 Hz is roughly 200 rows per second, tens of kilobytes.
  Every candidate here handles that with orders of magnitude of headroom; ClickHouse and PostgreSQL
  are built for problems this deployment does not have.
* **The risk is placement, not engine.** A synchronous insert or a per-row fsync inside the decode
  loop would destroy the throughput target regardless of which database wins. `ARCHITECTURE.md` §3
  already prescribes an egress stage of non-blocking broadcast channels, so the binding constraint is
  that persistence is a **bounded, drop-oldest subscriber with its own thread and drop counters** —
  never a backpressure source into ingest.

**Ordering dependency.** This decision interacts with `ADR-0005`. A snapshot-actor tracker hands a
writer immutable `Arc` snapshots, which makes persistence almost free; a sharded-`RwLock` tracker
makes a consistent snapshot a lock sweep. Persistence should therefore not be designed before the
concurrency model is chosen.

## Considered Options

1. **SQLite with WAL, optionally replicated by Litestream.** Bundled, no server, survives on a
   Raspberry Pi, and Litestream is a separate process (operational cost, not a dependency). Good for
   config and moderate history. Not clustering: restore is deliberate.
2. **redb.** Pure Rust, zero C dependency, tiny footprint — the right answer for static/embedded
   builds where shipping SQLite's C is unacceptable. Weakest on ad-hoc query and tooling: no
   `sqlite3` shell, no Litestream.
3. **PostgreSQL.** Correct for a centralised deployment where many receivers aggregate; wrong as a
   default for a receiver-local daemon, because a Pi should not need a database server.
4. **ClickHouse / Parquet.** Analytics-scale and export respectively. Both belong behind an adapter,
   never in the recording path.
5. **JSON-LD.** Not a store: a linked-data serialisation that needs ontology maintenance, and only
   pays off for semantic-web interop. Rejected as a storage choice.
6. **No persistence crate at all.** Recording happens by piping the existing JSON-lines egress into a
   file. Cheapest, but leaves replay non-self-describing and leaves every consumer to invent its own
   capture handling.

## Decision Outcome

Chosen: **a seam now, an engine later** — option 6's immediacy plus a defined boundary so option 1–4
can be adopted without touching the decode path.

* A crate `aerofoil-persistence` (`std`-only, an integrator in `miter deps --layers` terms) owning a
  `RecordSink` trait. It may depend on `aerofoil-common` and `aerofoil-tracker`; neither may ever
  depend on it.
* Implementation zero is JSONL, because it is already the egress format and needs no dependency
  beyond `serde_json`. It records **frames**, tagged with band, source and arrival time, so a capture
  is self-describing and replays deterministically — the property `ROADMAP.md` M3 already requires.
* Backends are features of that crate, not rewrites: SQLite first if the trigger fires, redb as the
  no-C alternative, PostgreSQL and ClickHouse strictly as adapters.
* Explicit non-goal: restoring live track state after a restart.

**What this record does not decide:** the storage engine, and with it the schema. That is a separate
record to be written when a trigger fires.

### Triggers for the engine decision

Either of these, not a date:

* A consumer needs a bounding-box/time query over more than an hour of history.
* A second receiver needs to aggregate into one store.

### Evidence required before that record is accepted

* **A benchmark spike, not vibes.** A ticket to be created (`spike`) comparing SQLite in WAL mode with
  batched commits against redb at 200–2000 tracks per second on Pi-class hardware, measuring p99
  commit latency as well as throughput, and — the part that actually matters — proving that decoder
  throughput is unchanged when the sink is saturated and dropping.
* A stated query requirement from a real consumer: which fields, which time window, which aggregation.

### Positive Consequences

* Recording lands early with no dependency, and satisfies a `ROADMAP.md` exit criterion that was
  otherwise unowned.
* The engine choice stays open until evidence exists, and cannot contaminate the decode path because
  the dependency direction is fixed.
* The snapshot-vs-lock question in `ADR-0005` is now known to have a storage consequence, so it gets
  decided with that in view rather than discovered afterwards.

### Negative Consequences

* Two hops through a trait for the first sink, when a `tee` would have done for a single-stream demo.
* A new crate name must be reserved on crates.io and added to `.gaugeblock/config.toml`
  `allowed_crates`, or the workspace allowlist will reject tickets scoped to it.
