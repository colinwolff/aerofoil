# 6. Choose the server egress transport surface

* Status: Proposed
* Date: 2026-11-04
* Deciders: Colin Wolff
* Related: `docs/SPEC.md` §5, `docs/ARCHITECTURE.md` §3, `docs/ROADMAP.md` §4

## Context and Problem Statement

`README.md`, `AGENTS.md`, `CONTRIBUTING.md` and `docs/ROADMAP.md` all assert SSE as a transport for
`aerofoil-server`. That assertion was never argued: the original charter listed **WebSocket**, the
rewrite of `docs/PROJECT.md` replaced it with SSE, and `docs/ARCHITECTURE.md` names only "TCP/gRPC"
without either. The server crate cannot be specified until the egress surface is a decision, and
`docs/SPEC.md` §5 has a row reserved for it.

The forces:

* **Traffic shape.** Egress is unidirectional: subscribers receive state-change events
  (`ARCHITECTURE.md` §3). Nothing in the current design requires a client to send anything after
  subscribing.
* **Client reality.** The plausible consumers are a shell (`curl`), a browser dashboard, a Rust/Python
  ingest client, and the MCP server. Only the dashboard is browser-native.
* **Operational simplicity.** The daemon is meant to run on a Raspberry Pi next to the receiver.
  Every protocol is another handshake, another keep-alive mechanism and another denial-of-service
  surface.
* **Backpressure.** `ROADMAP.md` §4 requires bounded queues and no unbounded growth. A protocol with
  no flow-control story makes that harder to honour honestly.
* **Testability.** The transport must be verifiable in Tier 3 without a browser in the loop.

## Considered Options

1. **SSE only** (`text/event-stream` over HTTP/1.1). Browser-native via `EventSource`, trivial for
   `curl`, text framing that matches JSON-lines. Costs: one-way only, reconnect/`Last-Event-ID`
   semantics must be implemented and tested, and HTTP/1.1 connection limits bite a browser opening
   many streams.
2. **WebSocket only.** Bidirectional, one connection for events plus future control messages. Costs:
   handshake, masking, ping/pong, fragmentation, and a second framing layer to specify and fuzz — for
   a capability nothing in the design currently needs.
3. **SSE for events and WebSocket for control.** Widest client compatibility, two code paths, two
   surfaces to test and document.
4. **gRPC server-streaming only.** Typed, versioned by protobuf, already committed for the ingest
   direction. Costs: browsers need a gRPC-Web proxy, and `curl` usability is lost without extra
   tooling.

## Decision Outcome

**Undecided.** Stays `Proposed` until the question below is answered, which must happen before
`aerofoil-server` is scaffolded; `storypole ask-decision` blocks that task until it resolves.

Deciding question: **does any client need to send commands (subscribe, retune, set filters) over the
same connection as the event stream?**

* If no → option 1 (SSE) plus option 4 (gRPC) as the typed path, and drop WebSocket from the docs.
* If yes → option 3, and the command surface must be specified in `docs/SPEC.md` §5 first.

### Positive Consequences of leaving it open

* The invented SSE assertion is now visible as a question instead of hardened into four documents.
* `docs/SPEC.md` §5 can name the transports once, from the outcome.

### Negative Consequences

* `aerofoil-server` cannot be designed against a transport it has not chosen, and the
  `enforce_readme_cli_flags` policy plus the README quickstart stay provisional.
* Whatever is chosen inherits the backpressure requirement in `ROADMAP.md` §4 immediately.
