# 8. Choose the long-term organisation handle

* Status: Proposed
* Date: 2026-11-04
* Deciders: Colin Wolff
* Related: `ADR-0007`, `storypole` `AF-21`

## Context and Problem Statement

`ADR-0007` put the repository and the eight crates under the maintainer account so the names could
be held immediately. That is a holding position, not an identity.

Two facts constrain what an organisation could be called:

* `aerofoil` itself is unavailable — `github.com/aerofoil` is a **user** account created 2023-12-27
  (display name "aerodyne"), and a taken username blocks an organisation of the same name.
* Every suffixed candidate checked on 2026-11-04 is free as both an organisation and a user:
  `aerofoil-labs`, `aerofoil-rs`, `aerofoil-hq`.

The project plausibly grows past one repository: a web frontend over the tracker, and crates that
bridge raw RTL-SDR sample streams into `aerofoil-1090` / `aerofoil-978` (explicitly out of scope for
the core decoders, `PROJECT.md` §2). An organisation is the usual home for that shape, and moving
later is cheap in GitHub terms (transfers redirect) but not free in crates.io terms (published
version metadata is immutable; only owner lists can change).

Concerns raised, to be weighed rather than waved away:

* **Discoverability and confusion.** "Aerofoil" is a common aerodynamics word, so search results are
  dominated by unrelated material. A suffix disambiguates the handle but also looks incidental. The
  worse confusion is the *existing* `github.com/aerofoil` user, which is not us.
* **Trademark.** A generic technical term is hard to defend and hard to enforce, and an org handle is
  not a mark in any case. If a protectable identity is ever wanted, a coined name beats
  `generic + generic suffix`; the project being open source lowers the stakes but does not create
  rights.
* **Cost of being late.** Once several repositories and published versions exist, renaming touches
  remotes, badges, docs and `Cargo.toml` metadata — but never the crates.io names, which are
  unaffected by an owner change.

## Considered Options

1. **`aerofoil-labs`** — free; says "this is the workshop around aerofoil" without claiming the
   plain word; broad enough to host a frontend, a driver bridge and the core crates.
2. **`aerofoil-rs`** — free; signals the Rust implementation explicitly, which is accurate today and
   narrows the identity if non-Rust frontends arrive later.
3. **`aerofoil-hq`** — free; neutral "headquarters" suffix, but the least informative of the three
   and the most likely to read as a marketing shell.
4. **Stay under the maintainer account** — zero migration cost, no second identity to keep in sync;
   scales poorly once outside contributors or sibling repositories appear.
5. **A coined, unrelated name** — strongest trademark position and no collision with aerodynamics
   content; but it abandons the recognisable term the crates are named after.

## Decision Outcome

**Undecided.** Stays `Proposed`.

Suggested trigger for deciding, rather than a date: **whichever comes first — a second repository
(the web frontend or the RTL-SDR bridge) or a second maintainer.** The recommendation at that point
is option 1 (`aerofoil-labs`), because it keeps the recognisable word while leaving room for
sibling projects, and it avoids implying a language commitment.

### Positive Consequences of leaving it open

* The irreversible part (names on crates.io) is already secured by `ADR-0007`; nothing is lost by
  waiting for the first satellite repository to reveal what the umbrella actually needs to be.
* Candidate availability is recorded, so the eventual decision starts from evidence rather than a
  fresh search.

### Negative Consequences

* Two identities may be in play for a while: `github.com/colinwolff/aerofoil` and whatever the
  organisation becomes, which an early adopter will notice.
* If someone claims `aerofoil-labs` in the meantime, the choice narrows to the remaining suffixes.
