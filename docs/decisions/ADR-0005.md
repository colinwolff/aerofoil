# 5. Choose the tracker concurrency model

* Status: Proposed
* Date: 2026-11-04
* Deciders: Colin Wolff
* Related: `ADR-0004`, `docs/SPEC.md` Invariant 10, `docs/ARCHITECTURE.md` §2.3

## Context and Problem Statement

`docs/ARCHITECTURE.md` describes `aerofoil-tracker` as a "sharded hash table partitioned across CPU
cores", then hedges: "64 independent striped `parking_lot::RwLock` segments **or** lock-free hash
primitives". `README.md` and `AGENTS.md` meanwhile assert the tracker is "lock-free". Those are two
different designs, and the tracker cannot be scaffolded until one is chosen.

The forces:

* **Read:write ratio.** Updates arrive at 1–10 Hz per aircraft from two bands; queries arrive from the
  MCP surface, the JSON-lines/SSE egress and gRPC subscribers. Reads plausibly outnumber writes by one
  to two orders of magnitude.
* **Hot-path filter.** `ADR-0004` requires `AddressFilter::is_verified` to answer on the decode path,
  per frame, so the read path must be allocation-free and never block on a writer for long.
* **Determinism.** `docs/SPEC.md` Invariant 10 requires monotonic per-field updates and a stable view
  for golden tests; weakly consistent iteration makes replay assertions harder to write.
* **Complexity budget.** A hand-written lock-free hash map with safe reclamation will not fit the
  250-line file ceiling (`AGENTS.md` §3.2) without becoming a third-party dependency.
* **Portability.** The tracker is `std` (it owns threads and TTL expiry), so `no_std` is *not* a
  driver here — unlike the decoders.

## Considered Options

1. **Striped `parking_lot::RwLock` shards.** N shards indexed by address bits; reads take a shared
   lock, writes an exclusive one. Simple, predictable, no unsafe, well-understood. Cost: writer
   latency under contention and iteration that must visit every shard.
2. **Lock-free concurrent map (e.g. `dashmap`) with epoch reclamation.** Best write concurrency and no
   lock convoy. Cost: a substantial dependency, weak iteration consistency, and trickier reasoning
   about the monotonic-field invariant.
3. **Single-writer actor publishing immutable snapshots (`arc-swap`).** Writers serialize through a
   channel; readers clone an `Arc` and never block. Excellent and deterministic read path, trivially
   safe iteration for queries. Cost: one write thread bounds ingest throughput, and every published
   generation costs an allocation plus copy-on-write of the shard.
4. **Per-field atomics over a seqlock-protected slot.** No locks anywhere, minimal footprint. Cost:
   the most unsafe code and the easiest place to introduce a torn multi-field read, which directly
   threatens Invariant 10's "one authoritative position per aircraft".

## Decision Outcome

**Undecided.** This record stays `Proposed` until the evidence below exists; the choice must be made
before `aerofoil-tracker` is scaffolded, and `storypole ask-decision` will block that task until it is.

Evidence required to decide:

* A measured read:write ratio from a recorded capture (updates per second versus query rate a real
  frontend needs), not an estimate.
* A micro-benchmark of options 1 and 3 at that ratio — they are the two realistic candidates, and
  option 3's allocation cost is the only thing likely to disqualify it.
* A decision on whether query iteration must be a consistent snapshot (option 3 wins) or may be
  best-effort (option 1 is sufficient).

### Positive Consequences of leaving it open

* The contradiction in `ARCHITECTURE.md` is now a recorded open question rather than two documents
  disagreeing, and `README.md`/`AGENTS.md` can stop asserting "lock-free" as fact.

### Negative Consequences

* Which type `aerofoil-tracker` exposes, and whether it is `Sync`, is unknown, so the frontend crates
  cannot be designed against it yet.
* The `AddressFilter` fast path (`ADR-0004`) cannot be benchmarked until the storage exists.
